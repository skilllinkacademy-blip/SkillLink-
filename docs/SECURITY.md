# אבטחה — SkillLink

## מודל האיום

האפליקציה היא SPA בלי שרת: ה-anon key של Supabase גלוי לכל מבקר, וכל אחד יכול לשלוח שאילתות PostgREST ישירות (בלי ה-UI). לכן ההנחה היא ש**הלקוח עוין**, וכל כלל הרשאה חייב להיאכף ב-Postgres עצמו באמצעות Row Level Security. JavaScript בצד הלקוח (למשל `ProtectedRoute`) הוא נוחות UX בלבד — לא שכבת אבטחה.

## מודל ההרשאות

שלושה שחקנים: **אורח (anon)**, **משתמש מחובר (authenticated)**, **אדמין** (שדה `role='admin'` ב-profiles).

| משאב | אורח | משתמש מחובר | הערות |
|---|---|---|---|
| `profiles` | קריאה | קריאה לכולם; עדכון לעצמו בלבד | פרופילים ציבוריים by design (מרקטפלייס) |
| `opportunities` | קריאה | קריאה; יצירה/עריכה/מחיקה לבעלים | |
| `opportunity_interests` | קריאה | הוספה בשם עצמו; מחיקה ע"י המתעניין או בעל ההזדמנות | |
| `conversations` | — | רק שיחות שהוא משתתף בהן | |
| `messages` | — | קריאה/כתיבה רק בשיחות שלו; שליחה רק בשם עצמו | הוקשח 2026-07-19 |
| `notifications` | — | קריאה/עדכון של שלו; שליחה רק כשולח מזוהה | התראות מערכת (sender NULL) — אדמין בלבד |
| `saved_opportunities` | — | רק שלו | |
| `reviews` | קריאה | כתיבה בשם עצמו בלבד; ביקורת אחת פר-פרופיל | `UNIQUE(profile_id, reviewer_id)` |
| `mentor_verifications` | — | רק שלו; אדמין רואה הכול | |
| Storage: תמונות ציבוריות | קריאה | העלאה רק לתיקיית `<uid>/` | avatars, covers, opportunity images |
| Storage: `mentor_id_docs` | — | קריאה: בעלים או אדמין | מסמכי זהות — פרטי |

## אימות מנטורים

1. מנטור מעלה מסמך מזהה ל-bucket הפרטי `mentor_id_docs` (נתיב `<uid>/...`).
2. נוצרת שורת `mentor_verifications` בסטטוס `pending` (אחת פר-משתמש, `UNIQUE(user_id)`).
3. אדמין רואה את הבקשות ב-AdminDashboard (policy ייעודי מאפשר לאדמין קריאה ועדכון).
4. אישור מציב `is_verified=true` בפרופיל, שולח התראת מערכת, ומציג תג ✓; דחייה שולחת התראה עם הסבר.
5. מנטור מאומת מקבל בונוס בציון ההתאמה.

## אבטחה מוכחת — בדיקות RLS

`supabase/tests/rls_tests.sql` — 16 בדיקות שרצות בטרנזקציה אחת (rollback בסוף): יוצרות שלושה משתמשים, מתחזות לכל אחד בדיוק כמו PostgREST (`set local role` + `request.jwt.claims`), ומוודאות גם חסימות (משתמש א' לא קורא הודעות של ב') וגם המשך תקינות (משתמש כן קורא את השיחות של עצמו, אורח כן רואה פרופילים).

**ממצאים אמיתיים שהבדיקות תפסו (ותוקנו ב-`20260719_tighten_messages_notifications_rls.sql`):**

1. **כתיבה לשיחות זרות** — ה-policy של `messages` היה `FOR ALL` עם `USING` בלבד (בלי `WITH CHECK`), כך שכל משתמש מחובר יכול היה להזריק הודעות לכל שיחה בפלטפורמה. הוחלף בארבעה policies מפורשים (SELECT/INSERT/UPDATE/DELETE) הכובלים הכול למשתתפי השיחה.
2. **זיוף התראות מערכת** — כל משתמש יכול היה להכניס התראה עם `sender_id IS NULL` (נחזית כהתראת מערכת) לכל משתמש אחר. עכשיו שולח חייב להיות `auth.uid()`, ו-NULL מותר רק לאדמין.

## פערים ידועים (לא מכוסים עדיין)

| פער | סיכון | המלצה |
|---|---|---|
| **פרטי קשר בפרופיל ציבוריים** | `phone` ו-`desired_salary` נקראים ע"י כל מחובר | לשקול policy עמודתי (view) או חשיפה רק לצדדים בשיחה פעילה |
| **Listing פתוח ב-buckets ציבוריים** | ניתן למנות את כל הקבצים (advisor warning) | לצמצם את policy ה-SELECT לנתיב ספציפי |
| **הגנת סיסמאות דלופות כבויה** | סיסמאות מוכרות-כדלופות מתקבלות | להדליק ב-Auth settings (HaveIBeenPwned) |
| **אימות אימייל כבוי** | הרשמה עם כל כתובת, בלי אימות בעלות | להדליק Confirm email לפני השקה רחבה |
| **פונקציות SECURITY DEFINER חשופות ל-anon** (`increment_likes` וכו') | שינוי מוני לייקים ללא אימות | `REVOKE EXECUTE FROM anon` |
| **אין rate limiting אפליקטיבי** | ספאם הודעות/התראות אפשרי בקצב גבוה | Supabase rate limits + כלל אפליקטיבי בהמשך |

## מפתחות AI — מוגן בצד שרת

קריאות ה-Gemini עוברות דרך Edge Function (`supabase/functions/gemini`) שמחזיקה את `GEMINI_API_KEY` ב-env של השרת בלבד. הלקוח קורא אליה עם ה-session שלו (`verify_jwt` מופעל — בקשה בלי token נדחית ב-401), ומפתח ה-AI לעולם לא נכלל ב-bundle. בנוסף הוסר `define: { 'process.env': env }` מ-Vite שקודם הזריק את *כל* קובץ ה-.env ל-bundle. אם ה-Function לא זמינה, הלקוח נופל בחזרה להיוריסטיקת ההתאמה המקומית — האפליקציה ממשיכה לעבוד בלי דירוג AI.

> הפעלה: `supabase secrets set GEMINI_API_KEY=<key>` (ראו LAUNCH_CHECKLIST.md).
